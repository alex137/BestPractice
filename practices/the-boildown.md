## Rule
**Every reply ends with a real markdown heading, `## The Boildown`, and nothing else may claim that heading** -- not "Next Steps", not a bold lead-in. **Under it, a bullet list, one line per item wherever the content allows it.** Every reply carries the first line and items 1 to 5; a reply ready to close the thread adds items 6 to 11 and ends on item 12, the archive line. The numbers are fixed, because other files cite them. This Rule is what to write, in order; the Detail section has each part in full under the heading named here, and the Story the incidents behind it.

### The first line, always: where the work is

**The first bullet, in every reply, opens "The work of this session is now on"** and names the branch the work is really on, with its repository ("The first line in full"):

- **The work of this session is now on:** `main` in BestPractice

**Read it from where the work is, not from what was asked**: "no branch yet" when nothing is written; a local branch not pushed yet says so after its name; an open pull request names the feature branch. Work on several branches or repositories names each. **When any of it is not landed, the line says so first, with counts** -- *"4 of 5 changes NOT on the landing branch yet (open pull requests); 1 is landed"* -- before it names any tier. A branch given up on purpose is named on a `**Branch disposition:** BRANCH -- drop (why)` line and not counted. **Enforced by the reply gate**: a first bullet that does not open this way is refused, and so is one that names a tier before the unlanded count (`require_first_item_leads_with_unlanded` in Precedent's `reply_check.json`).

### Every reply: five items, in this order

1. **Your next steps.** What the person needs to do now, in plain words -- no slug, no bare PR number, no reference that needs the thread open. A decision says what it actually is, and the session's own pick and why. **Every reply that still waits on an answer restates the question, standalone**: what is being decided, what yes and no each do, the session's pick and why, and what happens if the person says nothing. Never "the X question", "yes or no on X" or "as before" on their own; a pointer to where it was asked (opening words or time) is extra. **Enforced by the reply gate** (`require_ask_states_its_question`). A handoff carries which repository, the exact text to paste and how to report back; a click carries its link. **Never a push or a merge another session is already carrying out** -- say it is under way. **Nothing to do: say "Nothing blocking for you to do now."**, never a missing bullet. When item 12 holds the session on something the person must do, that action is named here. **A reply that finishes a plan asks "Do you want to act on this plan?"**, with what acting does and the pick, or says "I'm acting on this plan" and what that is, when it already is (`require_finished_plan_asks_to_act`). ("Item 1 in full".)
2. **What's blocking, if anything.** One sentence on what blocks the *session*, never the person's items above, and any major problem the session hit; skipped when nothing is. **Never skipped when item 12 says "Don't archive this session" for a reason on the session's own side**, an unfinished plan included: its `**Plan:**` line goes here. **When item 1 gives the person nothing to do, this line says what is running, where (linked), and when this session next acts** (`require_hold_names_what_runs`). ("Item 2 in full".)
3. **Work committed but NOT YET LANDED, whenever there is any.** Name the repository, the branch, how many commits that change files (never a merge or an empty commit), and recommend merging it. **Only work this session committed, on a branch or flow it worked on**, unless this session is blocked on or depends on other work: then name it and what it blocks. The reply gate prints what applies before the reply. ("Item 3 in full".)
4. **Band-aid or root fix, whenever this reply fixed something or recommended a fix.** One line per fix, opening **"Root fix:"** (name the cause) or **"Band-aid:"** (where the cause lives, what fixes it there, and whether that is done, handed off or not started, and why). **Say whether the bug came from upstream**, and where the upstream fix stands: done there, handed off or not started. The test is [upstream-fix](upstream-fix.md)'s point 7. ("Item 4 in full".)
5. **Optional, if anything.** On-topic for this thread and said plainly to be optional ("Optionally, you may want to..."); skipped when there is nothing.

**Never ask whether to add or remove repositories**, in any line or closing question; a repository the work needs and cannot reach is a handoff in item 1 ("Never ask about repositories").

**An item that sends the person to a separate issue checks `list_sessions` first.** If an active session is on it, the line is exactly: "Check \<session title\> (\<session link\>) to continue solving \<the issue\>." and nothing else; if none is, write the item as usual; if sessions cannot be listed, say so in a clause ("A separate issue goes to the session already on it").

**Nothing new is one line, never nothing** ("A check-in or Boildown with nothing new"). A turn where nothing visible or non-trivial to the person happened -- a wakeup, a reminder, a notification, the session's own `ReadNotifications` or polling -- says "Unchanged since the last update: still waiting on \<X\>." A Boildown whose every line would repeat the previous one is `- The work of this session is now on: <where it is>, unchanged since the last update.`, leading with the NOT-landed count while there is one, plus the Your next steps bullet restating any question still waiting (`require_section_not_repeated`).

**A batch of background jobs reports once** ("A batch of background jobs"). While another background command from this session is still running, or on a Monitor's progress event, the reply is one line in parentheses -- "(Waiting on the test run.)" -- and no Boildown; the report, with its Boildown, comes when the last job ends, and a failure may speak at once (`require_quiet_while_background_runs`).

### A reply that is ready to close the thread: seven more items, then the archive line

**Items 6 to 11 belong to the closing reply** -- it answers "Archive" or "Archive?", or the person is plainly done -- and are added only once all four conditions hold. Conditions 2 and 4 never decide the archive line in an ordinary reply ("The four conditions in full"):

1. **Nothing in the container that anybody wants to keep would be lost.** **Run [tools/precedent_container_safe.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_container_safe.py) and read its answer**; never answer from memory. Push or merge what it names before the archive line, or say plainly that it is meant to be lost, per checkout, on a `**Checkout disposition:** NAME -- discard (reason)` line. Refused blocking (`require_container_safe_if_says`).
2. **Nothing is left to do directly in this session**: no open pull request of its own, no question waiting on the person, no unread message from another session (`ReadNotifications` first), nothing queued to push. A non-blocking loose end does not fail it.
3. **No Routine is bound to this session**: check `list_triggers`.
4. **Nothing from the conversation lives only in the chat.** Re-read the whole conversation, compacted part included, list what it produced, and check each against the committed files. What is not in a document goes under item 1 on a bullet opening "Not yet in a document:", each with a suggested home and an offer to put it there; the same bullet may suggest restructuring this session's own documents, and a decision that belongs in a produced document.

When all four hold, add, in order:

6. **Retired 2026-10-30: no branches to delete.** The number stays; the branch cleanup page carries them.
7. **Other sessions on the same issue**, live and on this thread's subject: "Other relevant sessions to keep an eye on:", each linked. Omit when there are none.
8. **Sessions this one spawned**, each linked. Omit when there are none.
9. **At most one `Process idea:` and one `Content idea:`**, each one sentence, looked for in this session's work and the repository's last two weeks of commits; a kind that found nothing says where you looked. Only in the reply that says "You can archive this session." ("Items 6 to 11 in full" has the test for each kind.)
10. **A Todo worth a look, at most one. A due reminder comes first, by date** ([todo-reminder](todo-reminder.md)); otherwise one on this thread's subject, or one marked urgent or important, introduced as a change of subject.
11. **A compact check.** "Now is a good time to compact the session." when it would help and this is a clean point; when the reply gate says the offer is owed, it is due at the next clean point. Never "Not a cheap point to compact"; never beside "You can archive this session."
12. **The archive line, always last: "Don't archive this session." or "You can archive this session.", decided from the closed list of blockers below and nothing else**, in any reply, with the container scanner run first. The fixed sentence and nothing else: no clause after it, no reasoning before it, no word about a hook or scanner. The reason for "Don't archive" is already in item 1 or item 2. ("Item 12 in full".)

**Say "You can archive this session" whenever** nothing else is pending, everything is pushed to the landing branch, nothing in the temporary files is needed, and any plan is finished, continued in another session, or one the person said not to continue.

**Only a real blocker holds the line, and the list is closed:** (1) something wanted that exists only in the container; (2) a Routine bound to this session; (3) an action the person owes that the work cannot be finished or made safe without -- a push, a merge into the landing branch, an approval, an answer the session is stopped on; (4) something the session still has running or is waiting on, named on item 2's line; (5) a multi-step plan not finished. **A plan holds the line until every `- [ ]` step in its committed checklist is done**, linked on item 2's `**Plan:**` line, or until the person ends it early in their own words (`**Plan ended early:**`), or it is handed to a session `get_session` confirms is running it (`**Plan handed to:**`). **While the person owes a blocking action, the line is never "You can archive this session".** **Never a blocker:** a branch to delete, a suggestion, an optional follow-up, a question that does not change the outcome, or work on the landing branch not yet in `main` -- that gets one plain line before the archive line, *"Your changes are on `<landing branch>`, but not `main`."*

**Items 11 and 12 are recommendations the gate names but does not refuse; give the honest answer, and never comment on the gate itself** ("Item 12 in full").

### Moments other practices key on: named here, never restated there

**This practice owns two moments, and names them so other practices can
point at them instead of copying what they are:**

- **The archive-line reply** -- a reply whose item 12 says "You can archive
  this session." It can be any reply.
- **The closing reply** -- the reply that closes the thread: it answers
  "Archive" or "Archive?", or the person is plainly done. Conditions 2 and
  4 and the closing items 6 to 11 belong to it.

**A practice that fires at either moment names it** -- *"the archive-line
reply (the-boildown)"* -- in its occasion, gate note, tool text and Rule,
and never quotes the archive sentence or describes the closing reply in its
own words; a Rule sentence may explain the moment only beside its name. Named, it follows a change here with no edit of its own; restated, it
keeps the old moment and breaks without a sound, as two did in two days
(Story, 2026-10-20). `python3 tools/precedent_check.py --only
boildown-moments-named` refuses a restatement in this tree, in any source
that runs this engine's checks.

**Changing either moment starts from who keys on it.** Before a change to
what either moment is lands, run `python3 tools/precedent_moments.py` from
this checkout: it lists every practice, in every source checked out beside
it, that names each moment, and every one still restating it. The change
names those practices in its own commit or pull request, and each one that
restates the moment is moved to the name in the same change, or in its own
source by a handoff the change links.

## Detail
Everything under the headings below from "The heading and the list in full" on was the Rule's own text until 2026-10-31, moved here whole when the Rule was cut to what a reply must carry, in order (Story, 2026-10-31). The Rule names each heading where it needs it.

### Why one section, and where its items came from
**Why one section instead of several practices.** The six things this replaces were six separately-triggered rules, most of them reachable only through the reply gate, several of them enforced only in prose. Reading them side by side, they describe one artifact -- the closing block of a reply -- not six independent occasions. Naming it once, with a fixed name and a fixed order, is what makes it checkable: a bullet either appears in the right slot or it does not, which "a reply that made a commit should restate outstanding items" never quite was.

**"The Boildown" is deliberately not "Next Steps."** Everything in a reply is arguably "for" the person reading it, so a section literally titled that way names nothing -- and the phrase itself has an unrelated, friendlier reading that has nothing to do with a status report. "The Boildown" names what the section actually is: the reply reduced to what still needs a decision or an action, nothing else strained out. The first bullet under it is titled "Your next steps" for the same reason the whole section is not: within a section that already carries several kinds of information, the one bullet that is unambiguously the reader's own action items needs to say so on its own.

**Where the six inherited items came from, briefly, since their own files carry the full reasoning:**
- The plain-words self-contained ask, the recommendation riding alongside every decision, the repository-and-branch naming, and the "say explicitly when there's nothing" line all came from `next-steps-after-commit` and `asks-stand-alone`.
- The practice-suggestion bullet's four conditions are `merged-session-offers-a-practice`'s, unchanged.
- The spawned/other-session links and the three-things-always shape for a handoff (repository, exact paste text, way back) are `handoff-is-pasteable`'s.
- The one-unrelated-item cap on the Todo bullet, and its restriction to the closing reply only, are `closing-items-are-this-thread`'s.
- The three archive conditions, the ambiguous-case resolution (a minor suggestion or a question that doesn't change the outcome does not block an archive), and the fact that archiving buys back no compute, are `archive-a-finished-session`'s.

**What did not move here.** `session-spend-follows-the-task`'s guidance on picking a model for a spawned session's job is a different occasion -- it happens at session *creation*, not at the close of a reply -- and stays where it is, narrowed to just that half. Only its compact-offer clause and the mechanical requirement built for it moved into this practice.

This applies to every reply, not only one that made a commit: the point is a place the person can always look, not a report on what just happened.

**Under it, a bullet list, one line per item wherever the content allows it.** There are two shapes, and the second is the first with seven items added before the close.

### Item 2 in full: what's blocking
2. **What's blocking, if anything.** One sentence, on what is blocking the *session* -- never the items already covered in the bullet above, which are the person's to act on, not blockers. Skip this line entirely when nothing is blocking; do not write "nothing is blocking me." This is also where a major issue or problem the session hit belongs, in one sentence -- not a minor one, and not the earlier one this section spent months getting rid of about commits being behind or the wrong author name, which stays gone. **The one case this is never skipped: item 12 below says "Don't archive this session" for a reason that sits on the session's own side** -- something still running, something the session itself is waiting on that is not the person's to act on. A multi-step plan with steps still left is the same case: the `**Plan:**` line goes here. That has to be named here, not only gestured at by the archive line. **When item 1 gives the person nothing to do, this line says three things in plain words: what is running, where (the session or job, linked, or this session's own background task), and when this session next acts** -- *"step 3 is running in [the vendor session](https://claude.ai/code/session_...); I start step 4 when it reports back, about 15:35 Buenos Aires time."* A Plan line and a list of spawned sessions do not say it: to the person they read as a session that is idle and contradicting itself. Morgan, 2026-10-30 (strength: decided): *"You tell me not to archive this session, but you also tell me there's nothing for me to do. Are you doing anything? I looked and there's no background task, so I think you're not doing anything."* **Enforced by the reply gate** (`require_hold_names_what_runs`, id `boildown-hold-names-what-runs`): "Don't archive this session" beside a Your next steps that says nothing for the person is refused unless a line opening "What's blocking" carries all three; a reply carrying that line is no longer read as contradicting itself for saying "nothing blocking for you".

### Item 3 in full: work not yet landed
3. **Work committed but NOT YET LANDED, whenever there is any.** Committed, even pushed, but sitting on a branch the repository does not merge from -- a feature branch, a working branch, anything that is not that repo's own `base_branch`. **Name the repository, the branch, how many commits, and recommend merging it**, in this bullet, every time. **How many commits means the commits that change files** -- never a merge or an empty commit, and a branch that differs only in those has nothing unlanded ([verdict-not-mechanism](verdict-not-mechanism.md); Morgan, 2026-09-27, strength: decided). The same count goes for every line here that says one branch is ahead of or behind another. Morgan, 2026-09-21 (strength: decided): *"the Boildown MUST MUST tell me that and recommend I do that, so I don't miss doing it."*

   **Only the branch or flow this session worked on.** Item 3 reports work this session itself committed -- on a branch it worked on -- in this repository or any other. Work this session did not touch gets no line, in this repository or another: not another session's unlanded work, not a sibling practice source's branches, not even as an optional line. **The one exception is work this session is literally blocked on or depends on** -- a change here that cannot land or cannot work until that other work reaches its branch -- and then the line names it and says what it blocks. The reply gate applies the first test for you, by the session trailer on the commits; the exception is the session's own judgment, because only the session knows what its work depends on. Morgan, 2026-09-29 (strength: decided): report only the branch or flow worked on in that session window, unless the session is blocked on other work.

   **Why this is its own item and not a corner of item 1.** Two mechanisms already look near this and neither answers it. The stop hook refuses a turn ending with uncommitted or unpushed work -- but it fires AFTER the reply is composed, so it can only reject the turn and cost the person the reply twice; it can never put a line in the Boildown. And *pushed* is not the question: a feature branch can be pushed, green, and perfectly safe while the work sits where nothing merges from, which is exactly the state that gets forgotten. **[tools/precedent_gate.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_gate.py)'s reply gate prints it before the reply**, for this checkout and every sibling Precedent repo, wherever the commits are this session's own, so the sentence is in front of the session at the one moment it can still be written. Skip the bullet only when there is genuinely nothing unlanded anywhere.

### Item 4 in full: band-aid or root fix

   - **"Band-aid:"** it clears this instance, and the cause is still there. Then say **where the cause lives and what fixes it there** -- a template, a generator, a vendored copy, a practice, whatever [upstream-fix](upstream-fix.md) finds -- and where that root fix stands: done in this reply, handed off (link the prompt or the session), or not started, and why. **A band-aid with no root fix named has not answered this bullet.**

If it did, the line names the repository that owns it and where the upstream fix stands: **done there** (link it), **handed off** (link the Prompt Please block or the session carrying it), or **not started**, and why. Morgan, 2026-09-28 (strength: decided): *"any fixes that were applied to problems that were found in the session ... do those fixes need to be applied upstream to the vendored in products?"*

   A reply with several fixes gives each its own line. The test for which label applies is [upstream-fix](upstream-fix.md)'s point 7: does the fix survive a fresh container, and does someone who was not here get it without being told? A fix that fails either is a band-aid, however correct it is. Skip the bullet when the reply neither made nor recommended a fix. Morgan, 2026-09-26 (strength: decided): *"IF you committed a fix or did a prompt or doc to recommend a fix -- in that case, tell me if your fix is a temporary band-aid fix, or if it's fixed at the root."*

### Item 5 in full: optional
5. **Optional, if anything.** Something useful but not required, on-topic for this thread -- never an item that belongs to a different session's work. Say plainly that it is optional: "Optionally, you may want to...", with a link and exact wording where one applies. Skip the line entirely when there is nothing.

### Never ask about repositories

Which repositories a session holds is the session's own check, made before the work starts and acted on silently ([prompt-please](prompt-please.md)'s repository check); a repository the work genuinely needs and cannot reach is a handoff in item 1, named concretely, never an open question. This holds whatever other practice or habit prompts the question. Morgan, 2026-09-28 (strength: decided): *"we rarely ever do, and I think it's confusing and just adds noise. ### A separate issue goes to the session already on it
**Any item that sends the person to a separate issue, problem or bug checks first whether a live session is already on it.** Whenever a Boildown item recommends looking into something other than this thread's own work -- a bug the session tripped over, a major problem item 2 names, an optional follow-up in item 5, the Todo in item 10, a handoff in item 1 -- run `list_sessions` before writing the line, and read the likeliest matches (`get_session` where a title alone does not settle it). **If an active session is working on it, the line is exactly: "Check \<session title\> (\<session link\>) to continue solving \<the issue\>."** -- its real title, its full `https://claude.ai/code/session_...` link, and the issue named in plain words that make sense without this thread open. Nothing else goes with it: no paste block, no suggestion to start a fresh session, no restatement of the fix -- a second session on the same problem is the thing this prevents. Active means not archived; a session idle with the issue still unresolved counts, and so does one blocked waiting on the person, which is the case that most needs routing there. **If no session is on it, the item is written exactly as it would be otherwise.** If this session cannot list sessions at all, the line says so in a clause rather than quietly skipping the check.

### A check-in or Boildown with nothing new
**A check-in that finds nothing new does not get a fresh Boildown reworded from scratch.** This is not only a scheduled wakeup, a reminder firing, or a background-task notification -- it is any turn where nothing happened that is visible, or non-trivial, to the person, whatever set it off. That includes a turn the stop hook itself forces: on 2026-09-20 a practice-candidate detector fired twice on its own prior boilerplate, and each recheck was a full turn with nothing to tell the person beyond "still not a rule." A turn like that says so in one line -- "Unchanged since the last update: still waiting on \<X\>." -- and stops there, rather than re-deriving the same items in different words each time; restating the identical status in new phrasing is not a fresher answer, it is the same answer costing another read. Where the check-in exists only to confirm nothing changed and nothing else in the turn calls for a reply, send that one line and nothing more rather than manufacture a fuller reply to satisfy this section. Not nothing: an empty turn makes the harness ask for "visible output" and the session has to answer anyway (2026-10-06). This does not relax the requirement for a reply that has something to say; it only removes the reason to invent a repeat when there is nothing to add.

**A Boildown with nothing new in it is one line.** When every line of it would say again what the previous reply's Boildown said -- the same branch, the same ask, the same archive verdict, however it is reworded -- the whole section is one line: `- The work of this session is now on: <where it is>, unchanged since the last update.` That still opens on where the work is, as the first bullet must. **While some of this session's work is not landed, the one line leads with it**, as the first line always must: `- The work of this session is now on: N branch(es) NOT landed yet (<names>), and <where the rest is>; unchanged since the last update.` (2026-10-20: one refusal asked for the plain one line and for the not-landed lead together, and the plain form has no room for the count; the refusal now hands over this form when it applies.) **A question still waiting on the person is never folded into that one line**: the short form is the one line plus the Your next steps bullet restating the question in full, as item 1 requires, and the repeat check does not count that bullet (2026-10-29: the one-line form had been dropping it, and sessions wrote "the voice pack question, as before" instead). A Boildown that adds even one new line is a real update and keeps its full shape. Morgan, 2026-10-05 (strength: decided): *"a boildown with nothing should be one line"*, after three in a row repeated the same branch line and archive verdict around a single new fact. **Enforced at both ends of the turn.** At its start, the reply gate shows the previous reply's Boildown and this one-line form, so the repeat is never written. At its end, the stop hook refuses a Boildown whose every line repeats the previous one, and asks for nothing further -- the repeat is already on screen, and a correction would be more of the same. Both read `require_section_not_repeated` in Precedent's `reply_check.json`; how alike two lines must be to count as a repeat is calibrated in [tools/precedent_reply_check.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_reply_check.py)'s `item_repeats`, and a branch or link that changed is always a change.

### A batch of background jobs
**A batch of background jobs reports once.** When a background job wakes the turn while another background command from this session is still running, or the wake is only a progress event from a Monitor, the reply is at most one line in parentheses naming the wait -- "(Waiting on the test run.)" -- and nothing else: no status report, no Boildown. Act on the wake if it needs acting on, and end the turn. **The report comes once, when the last job ends, and carries the Boildown as any reply does**; a wake that reports a failure may speak at once, because a failure is the one thing worth hearing early. Morgan, 2026-10-05 (strength: decided), after four Debuts run in sequence reported themselves one at a time, each with its own Boildown: a reply to a job finishing gets no Boildown unless the job is done, and a batch reports once. **Enforced at the stop hook**: `require_quiet_while_background_runs` in Precedent's `reply_check.json` refuses anything more than that one line on such a turn, and its refusal asks for the one line, and the reply gate prints the rule at the start of the turn that starts the batch. Which jobs are still running is read from the transcript by [tools/precedent_reply_check.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_reply_check.py)'s `turn_wake`, which counts only commands started in the background with Bash; a job started another way is not counted, so its batch may be judged finished early, and then the session speaks as it did before. A harness nudge to say what you are doing does not override this: the person's rule governs, and the batch's one report answers it.

**A session's own housekeeping call is the same case, not a different one.** Calling `ReadNotifications` (or anything of the same shape -- polling a Routine, checking a subscribed PR, glancing at a queue) is never itself something that happened *to the person*; only what it turns up is. Finding nothing there, or finding only what an earlier reply in the same thread already covered, means the turn still has nothing new to report -- the one-line "Unchanged since the last update" template, same as any other no-op check-in. The activity being on the session's own side is exactly why it does not count: a person reading three Boildowns in a row, each reworded, for a stretch where the only thing that happened was the session checking its own inbox, is reading the cost of that checking, not news.

Where one does, the bullet says which decision and which document. ### Item 12 in full: the archive line and its blockers
12. **The archive line, always last, always one of two fixed sentences, decided from the closed list of blockers below and nothing else.** Any one of them: "Don't archive this session." None: "You can archive this session." -- in any reply, with the closing items above not done and the conversation not re-read, because those wait for the closing reply and archiving loses neither (the scanner in condition 1 is still run first, since it is cheap and is what "nothing lost" means). Morgan, 2026-10-18 (strength: decided), after a session said "Don't archive" for three replies with nothing running, nothing unlanded and nothing waiting on him. **This sentence is never the whole explanation.** By the time it appears, item 1 or item 2 above has already said, concretely, which one it is: an explicit action item blocked on the person (item 1), or something the session itself is still waiting on or has running in the background (item 2). The archive line only names the verdict; the numbered items above it are where the reason actually lives, and a "Don't archive this session" with no reason findable in either one is the exact failure this whole section exists to prevent.

   **The line is the fixed sentence and nothing else -- decide it, never argue it.** No clause after it ("...until you've pasted the prompt"), no sentence before it explaining how the session reached the verdict, and never a word about what a hook, scanner or notice listed or would accept. Whatever the person must do before archiving is already item 1, written as the action itself; whatever the session is still waiting on is already item 2. A person who wants the reasoning asks for it. Morgan, 2026-09-26 (strength: decided): *"You should just decide whether to say to archive this session or not. You do not need to share your thinking about whether, why you came to that conclusion. If I have a question, I will ask. And in that boil down section, it should already say anything that I need to do that would block your archive suggestion."*

**And "the work" in condition 1 means everything in the container, not this session's own deliverable.** A session reads that condition against the clone it has been working in, because that is the clone `git status` answers for and because "the work" reads as "the thing I was asked to do". Both readings are natural and both are too narrow: a container here routinely holds five or six checkouts -- this repo, a second copy of it under a different HOME, one per practice source -- and archiving releases all of them at once. On 2026-09-22 a reply correctly reported its own eight commits pushed, said the archive line, and left six unpushed commits in a source clone it had never looked at. **Run the scanner, in every reply that is about to say the line**; "I pushed my work" is not an answer to the question condition 1 actually asks.

**The test, in Morgan's words, is the standing rule for this line.** A session can say "You can archive this session", and must say it, when all of these hold: nothing else is pending; everything is pushed to the landing branch; nothing in the temporary files is needed; and any plan it was following is finished, continued in another session, or one the person said not to continue. When they all hold, the line is never withheld; when one fails, it is the blocker the list below names. Morgan, 2026-10-19 (strength: decided): *"if a session has nothing else pending, nothing that wasn't pushed to [the landing branch], nothing on in the temporary files that's needed, and the plan is being continued in another session, or I said that I don't want to continue the plan, then you can say, and you should say, it can be archived."*

**Only a real blocker can hold the line, and the list of them is closed.** "Don't archive this session" is said for one of these and nothing else: (1) something in the container that somebody wants to keep and that exists only there -- the scanner in condition 1 names it; (2) a Routine bound to this session (condition 3); (3) an action the person owes that the work cannot be finished or made safe without -- a push, a merge, an approval, an answer the session is stopped on; (4) something the session itself still has running or is waiting on, named on item 2's line with where it runs and when the session next acts; (5) a multi-step plan the session is following that is not finished. **A plan holds the line until every step of it is done, or until the person says, in their own words, that they are finishing it early** -- never on the session's own sense that the rest can wait, and never because the steps left look small. A plan a session follows keeps its steps as a `- [ ]` checklist in a committed file, ticked as each one lands. Item 2 names it: the plan, as a link, and the steps still left, in plain words -- one line, opening `**Plan:**` and the link, so the reply check can read the plan's checklist and refuse "You can archive this session" while a box in it is still unticked. A person who ends the plan early is quoted on a line opening `**Plan ended early:**`. **A plan handed to another session no longer holds this one open**, once `get_session` confirms that session is running and the plan is in its hands: a line opening `**Plan handed to:**` gives that session's link and where the plan now lives. Morgan, 2026-10-19 (strength: decided): *"if your session is following a multi-step plan. You cannot tell me to archive it unless the plan is fully complete Or I explicitly tell you that I am finishing the plan early."* **Everything else is not a blocker and never holds the line**: a branch to delete, first of all -- a used-up branch is housekeeping for the branch cleanup page, never item 1 and never the reason under this line -- and equally a suggestion, an optional follow-up, a question that does not change the outcome.

**Nor is anything still to go into main.** Work that has reached the landing branch is on `origin`, and a merge into `main` can run from any session, whenever the person chooses: a person often lands several sessions on the landing branch and moves them into `main` together. **So "waiting for your go-ahead to Produce" is never blocker (3)**, and never the reason for "Don't archive this session". The line is "You can archive this session", and one plain line before it says where the work stopped: *"Your changes are on `<landing branch>`, but not `main`."* That line is the warning; it never becomes a hold. Morgan, 2026-10-18 (strength: decided): *"never stop an archive because something is not on main. That requires a message and warning to me, but it shouldn't stop the archiving."* Morgan, 2026-09-26 (strength: decided): *"if a branch needs a deletion, that should never be a blocker and it should never be a reason to tell the user don't archive this session. Only blockers (such as uncommitted branch) can be used to say that."*

**If the person still owes a blocking action, the archive line is never "You can archive this session" -- no exceptions.** A push, a merge into the landing branch (never one onward into `main`, above), an approval, an answer the session cannot proceed without -- anything named in item 1 as still theirs to do before this is actually safe or done fails condition 1 or 2 above on its own, and the line is "Don't archive this session" every time, full stop, until that action is taken and confirmed. This is not a new condition -- it is the existing three read correctly -- but it is stated here on its own, in words that cannot be softened into "probably fine to close," because the fixed sentence is exactly the part a session under-reads when the rest of the reply feels finished.

**Items 11 and 12, and the compact offer below, are recommendations, not a binding shape.** Give the honest answer after actually reviewing which situation applies -- if the session can be archived, say so; if it can't, say so; if this is a good point to compact, say so -- but nothing here refuses a turn for omitting one. `reply_check.json` still NAMES an unmet one (`--explain` shows it, `advisory: true`), and tools/precedent_reply_check.py still detects it, but neither blocks on it -- unlike the heading in the rule above, which still does. This changed 2026-09-17, on Morgan's own instruction after this gate blocked several turns over content it had no way to know was true or false; see Story.

**Never comment ON the gate itself.** No "I'm not going to say the archive line," no explaining that a requirement is advisory, no narrating compliance or refusal of it -- give the assessment, or leave the bullet out because it plainly does not apply, the same way every other optional item on this list is handled. The gate is plumbing; talking about the plumbing in a reply is exactly the kind of thing this whole practice exists to keep out of the person's way.

**When a compact offer is owed.** Once this conversation has grown 100,000 tokens since a reply last said "Now is a good time to compact the session." (or "This is a cheap point to compact", the older wording, which still counts), the offer is owed. **The session does not have to guess whether it is**: the turn-start reply gate reads the transcript and prints "a compact offer is owed" in that turn, and prints nothing about compacting otherwise. Item 11 is then due, as it says, and stays due turn after turn until it is given. **The one exception is unchanged: a reply whose own archive line says "You can archive this session" says nothing about compacting at all.**

## Why
Six practices asking for six related things, loaded through five different channels (a bare `gates: ["reply"]` registration, an occasion-index entry, a private individual set, a second private individual set, and a JSON declaration each of `reply_check.json` and `close_detect.json`), produced exactly what you would expect: some of it landed every time, some of it only when a session happened to recognize the occasion, and telling which was which meant reading five files. One section, one heading, one fixed order removes that question -- either the bullet the person is looking for is in its slot, or the practice was not followed, and there is no third case to puzzle over.

## Install
Enforced the same way `next-steps-after-commit` and `session-spend-follows-the-task` were, with one change since 2026-09-17: `reply_check.json` declares the required heading pattern (still blocking) and the two fixed sentence-pairs (archive, compact -- now `advisory: true`, each its own entry), and [tools/precedent_reply_check.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_reply_check.py) refuses a reply missing the heading via the Stop hook, same as before, but only NAMES an unmet advisory sentence rather than refusing over it -- `violations()` still detects it, `main()` no longer lets it into the blocking set. `close_detect.json` declares this practice's slug and the archive-ready phrase for [tools/precedent_close_detect.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_close_detect.py), which still gates the practice-idea bullet on real evidence from the session's own transcript rather than on the occasion alone. Neither script needed changing for the original consolidation -- only the JSON declarations moved, from the two practices this absorbs to this one; [tools/precedent_reply_check.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_reply_check.py) itself changed only for the 2026-09-17 advisory split.

**The compact offer is worked out before the reply, not checked after it** (2026-09-28). `reply-gate.sh`, at UserPromptSubmit, passes the hook's `transcript_path` to [tools/precedent_gate.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_gate.py) as `PRECEDENT_TRANSCRIPT_PATH`, and the reply gate runs the same `offer_is_due()` the stop hook uses. Owed: it prints that the offer is owed and how far the conversation has grown. Not owed: it prints nothing about compacting. No transcript (an older hook, a hand run): it says it could not tell, rather than claiming the stop hook will.

What stays a matter of judgment, as it always was: whether an ask is genuinely self-contained, whether a recommendation is real rather than filler, whether a Todo is a good enough fit to mention, whether a moment is actually cheap to compact, and, since 2026-09-20, whether a "Don't archive this session" line has a real reason sitting in item 1 or item 2 above it. That last one was tried against the existing mechanism before being left this way: `require_one_of` can detect the fixed sentence, but detecting whether the *surrounding prose* names a concrete action versus reads as a content-free recap is the same unsolved problem as "is this recommendation real rather than filler" two items over -- no regex distinguishes "waiting on the billing number you're pulling" from three bullets that happen to precede the sentence. No script can read a chat reply for those; the fixed shape only guarantees the section exists and is in order, which is what makes everything missing from it visible.

**One thing moved OFF that list on 2026-09-22, and only one**: whether archive condition 1 holds. The archive VERDICT is still a judgment call for exactly the reasons above -- it turns on whether a loose end is blocking, which no regex reads. But condition 1 is not a reading of the reply at all; it is a question about the disk, and [tools/precedent_container_safe.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_container_safe.py) answers it by looking: every git checkout the container holds, scanned for uncommitted changes, untracked files, and commits no remote can reach. `reply_check.json`'s `require_container_safe_if_says` runs it whenever a reply says "You can archive this session" and refuses the turn -- blocking, unlike the sentence requirement it sits beside -- naming each checkout and what is only there. Engine output a refresh writes into a source clone and deliberately never commits is excluded, via `precedent_refresh_sources.classify_dirt`, which is the one definition of which paths those are; counting it would make every clone permanently unsafe and teach a session to ignore the answer. An engine vendored before the scanner existed reports nothing and blocks nothing, the same way an unknown predicate does.
