## Rule
**Every reply ends with a real markdown heading, `## The Boildown`, and nothing else may claim that heading.** Not "Next Steps", not a bold lead-in -- a bold line is exactly what the rest of a reply is already full of, and it does not survive being skimmed. This applies to every reply, not only one that made a commit: the point is a place the person can always look, not a report on what just happened.

**Under it, a bullet list, one line per item wherever the content allows it.** There are two shapes, and the second is the first with seven items added before the close.

### Every reply: five items, in this order

1. **Your next steps.** What the person needs to do now, named in plain words -- no slug, no bare PR number, no reference that only makes sense with the thread open. If it names a decision, say what the decision actually is, and say what the session itself would do and why, in the same clause -- an ask that hands over the question and keeps the answer has moved the work, not done it. If it sends the person to another session, it carries that handoff's three things: which repository, the exact text to paste, and how to report back -- written for a reader who cannot see this conversation. If it means clicking somewhere, the link is there. **Never a Promote, a `Go update` or a merge that another session is already carrying out on the same work** -- say that it is under way instead ([promote](promote.md)). **If there is nothing, say so explicitly** -- "Nothing blocking for you to do now." -- never silence and never dropping the bullet because it would be empty. **If item 12 below is going to say "Don't archive this session" because of something the person needs to do, that action is named here, concretely** -- "Nothing blocking for you to do now." and "Don't archive this session." never appear in the same reply; one of them is wrong.
2. **What's blocking, if anything.** One sentence, on what is blocking the *session* -- never the items already covered in the bullet above, which are the person's to act on, not blockers. Skip this line entirely when nothing is blocking; do not write "nothing is blocking me." This is also where a major issue or problem the session hit belongs, in one sentence -- not a minor one, and not the earlier one this section spent months getting rid of about commits being behind or the wrong author name, which stays gone. **The one case this is never skipped: item 12 below says "Don't archive this session" for a reason that sits on the session's own side** -- something still running, something the session itself is waiting on that is not the person's to act on. That has to be named here, not only gestured at by the archive line.
3. **Work committed but NOT YET LANDED, whenever there is any.** Committed, even pushed, but sitting on a branch the repository does not merge from -- a feature branch, a working branch, anything that is not that repo's own `base_branch`. **Name the repository, the branch, how many commits, and recommend merging it**, in this bullet, every time. **How many commits means the commits that change files** -- never a merge or an empty commit, and a branch that differs only in those has nothing unlanded ([verdict-not-mechanism](verdict-not-mechanism.md); Morgan, 2026-09-27, strength: decided). The same count goes for every line here that says one branch is ahead of or behind another, the Promote line included. Morgan, 2026-09-21 (strength: decided): *"the Boildown MUST MUST tell me that and recommend I do that, so I don't miss doing it."*

   **Why this is its own item and not a corner of item 1.** Two mechanisms already look near this and neither answers it. The stop hook refuses a turn ending with uncommitted or unpushed work -- but it fires AFTER the reply is composed, so it can only reject the turn and cost the person the reply twice; it can never put a line in the Boildown. And *pushed* is not the question: a feature branch can be pushed, green, and perfectly safe while the work sits where nothing merges from, which is exactly the state that gets forgotten. **[tools/precedent_gate.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_gate.py)'s reply gate prints it before the reply**, for this checkout and every sibling Precedent repo, so the sentence is in front of the session at the one moment it can still be written. Skip the bullet only when there is genuinely nothing unlanded anywhere.

4. **Band-aid or root fix, whenever this reply fixed something or recommended a fix.** That covers a fix the session committed and a fix it handed over for someone else to make: a paste-ready prompt, a doc, a Todo, or a recommendation in the reply itself. **The bullet opens with one of two labels and says which in plain words:**
   - **"Root fix:"** the change removes what caused the problem, not just this instance of it. Name the cause in a few words.
   - **"Band-aid:"** it clears this instance, and the cause is still there. Then say **where the cause lives and what fixes it there** -- a template, a generator, a vendored copy, a practice, whatever [upstream-fix](upstream-fix.md) finds -- and where that root fix stands: done in this reply, handed off (link the prompt or the session), or not started, and why. **A band-aid with no root fix named has not answered this bullet.**

   **Every fix line also says whether the bug came from upstream** -- a file this repository did not write: a vendored engine or catalogue, a check a practice set ships, anything from a template. If it did, the line names the repository that owns it and where the upstream fix stands: **done there** (link it), **handed off** (link the Prompt Please block or the session carrying it), or **not started**, and why. A fix made to the local copy of an upstream bug is a band-aid by definition, and [upstream-bug-stops-here](upstream-bug-stops-here.md) says it should not have been made without the person asking. Morgan, 2026-09-28 (strength: decided): *"any fixes that were applied to problems that were found in the session ... do those fixes need to be applied upstream to the vendored in products?"*

   A reply with several fixes gives each its own line. The test for which label applies is [durable-fix](durable-fix.md)'s: does the fix survive a fresh container, and does someone who was not here get it without being told? A fix that fails either is a band-aid, however correct it is. Skip the bullet when the reply neither made nor recommended a fix. Morgan, 2026-09-26 (strength: decided): *"IF you committed a fix or did a prompt or doc to recommend a fix -- in that case, tell me if your fix is a temporary band-aid fix, or if it's fixed at the root."*

   **Why a Boildown item and not only durable-fix.** durable-fix has asked for this since 2026-09-08, and in practice it rarely surfaced. It has no file to match, so it reaches a session only through the reply and review gates, as one line among about thirty, and it arrives when the reply is being written, after the fix has already been chosen. Nothing marked the place where the answer should have been, so leaving it out cost nothing anyone could see. A fixed slot makes the gap visible, which is the same reason item 3 is its own bullet.

5. **Optional, if anything.** Something useful but not required, on-topic for this thread -- never an item that belongs to a different session's work. Say plainly that it is optional: "Optionally, you may want to...", with a link and exact wording where one applies. Skip the line entirely when there is nothing.

**Never ask whether to add or remove repositories.** No Boildown line, and no closing question anywhere in the reply, asks the person whether there are other repositories to attach, add, drop or take away. Which repositories a session holds is the session's own check, made before the work starts and acted on silently ([prompt-please](prompt-please.md)'s repository check); a repository the work genuinely needs and cannot reach is a handoff in item 1, named concretely, never an open question. This holds whatever other practice or habit prompts the question. Morgan, 2026-09-28 (strength: decided): *"we rarely ever do, and I think it's confusing and just adds noise. So let's have it no longer ask that at the end"* -- and, on it not being found as a rule anywhere: *"regardless, other practice or not, we should not do that."*

**Any item that sends the person to a separate issue, problem or bug checks first whether a live session is already on it.** Whenever a Boildown item recommends looking into something other than this thread's own work -- a bug the session tripped over, a major problem item 2 names, an optional follow-up in item 5, the Todo in item 10, a handoff in item 1 -- run `list_sessions` before writing the line, and read the likeliest matches (`get_session` where a title alone does not settle it). **If an active session is working on it, the line is exactly: "Check \<session title\> (\<session link\>) to continue solving \<the issue\>."** -- its real title, its full `https://claude.ai/code/session_...` link, and the issue named in plain words that make sense without this thread open. Nothing else goes with it: no paste block, no suggestion to start a fresh session, no restatement of the fix -- a second session on the same problem is the thing this prevents. Active means not archived; a session idle with the issue still unresolved counts, and so does one blocked waiting on the person, which is the case that most needs routing there. **If no session is on it, the item is written exactly as it would be otherwise.** If this session cannot list sessions at all, the line says so in a clause rather than quietly skipping the check.

**A check-in that finds nothing new does not get a fresh Boildown reworded from scratch.** This is not only a scheduled wakeup, a reminder firing, or a background-task notification -- it is any turn where nothing happened that is visible, or non-trivial, to the person, whatever set it off. That includes a turn the stop hook itself forces: on 2026-09-20 a practice-candidate detector fired twice on its own prior boilerplate, and each recheck was a full turn with nothing to tell the person beyond "still not a rule." A turn like that says so in one line -- "Unchanged since the last update: still waiting on \<X\>." -- and stops there, rather than re-deriving the same items in different words each time; restating the identical status in new phrasing is not a fresher answer, it is the same answer costing another read. Where the check-in exists only to confirm nothing changed and nothing else in the turn calls for a reply, prefer sending none at all over manufacturing one to satisfy this section: the heading requirement binds a reply that gets sent, not the decision to send one -- a turn with no prose has no Boildown to check, same as it always did. This does not relax the requirement for a reply that has something to say; it only removes the reason to invent a repeat when there is nothing to add.

**A session's own housekeeping call is the same case, not a different one.** Calling `ReadNotifications` (or anything of the same shape -- polling a Routine, checking a subscribed PR, glancing at a queue) is never itself something that happened *to the person*; only what it turns up is. Finding nothing there, or finding only what an earlier reply in the same thread already covered, means the turn still has nothing new to report -- the one-line "Unchanged since the last update" template, or no reply at all, same as any other no-op check-in. The activity being on the session's own side is exactly why it does not count: a person reading three Boildowns in a row, each reworded, for a stretch where the only thing that happened was the session checking its own inbox, is reading the cost of that checking, not news.

### A reply that is ready to close the thread: seven more items, then the archive line

A reply may only add these once the three conditions below all hold -- the same three that gate the archive line, checked first:

1. **NOTHING IN THE CONTAINER THAT ANYBODY WANTS TO KEEP WOULD BE LOST** -- every checkout it holds, not just the one this session was working in, and not just the work this session did. Pushed, merged, published, or deliberately abandoned, and a published artifact is safe the moment it publishes, with no separate push to wait for. **Run [tools/precedent_container_safe.py](../tools/precedent_container_safe.py) and read its answer; do not answer this from memory.** It scans every git checkout in the container -- this repo, its siblings, the home directory's clones, whatever the source config declares -- for uncommitted changes, untracked files, and commits no remote can reach, and exits non-zero when any of it is only here. **Anything it names is pushed or merged BEFORE the archive line is written, never named in the reply as a caveat beside it**; the one alternative is saying plainly, in the reply, that it is meant to be lost. Morgan, 2026-09-22 (strength: decided): *"if changes are done locally but not pushed to main or precedent-beta-v01 then never never recommend 'You can archive this session' (unless the work is intended to be lost!) - this is very important"*. The reply gate refuses the turn on this one, and refuses it blocking rather than advisory, unlike the archive sentence itself: `require_container_safe_if_says` in [reply_check.json](https://github.com/alex137/BestPractice/blob/staging/reply_check.json).
2. **Nothing is left to do directly in this session** -- no open pull request of its own, no question still waiting on the person, nothing queued to push, no other action that has to happen in this specific window. A non-blocking loose end does not fail this -- a minor suggestion, a question that doesn't change what happens next, something the reply says it is waiting on that will not change the result. Name it and move on; it does not hold the close open.

   **A Promote still to run never fails this condition, and is never a reason to say "Don't archive this session."** Work that has landed on pre-staging is on `origin`; moving it to staging is the pipeline's next step toward live, whenever the person chooses, and no window has to stay open for it -- any session can run it later. It gets its one plain line in The Boildown and nothing more: never item 1's next steps, never item 2's blockers, never the reason behind the archive line. **While another window is already promoting that repository, it gets no line at all** -- no reminder, no suggestion, at most a plain statement that a Promote is under way. The reply gate checks the Promote lock and says which of the two a repository gets, so a session never has to guess; a claim older than the lock's 15 minutes is not a Promote running. Morgan, 2026-09-27 (strength: decided), after the per-turn line told him "a Promote can move them" twice while another window was promoting: *"NEVER recommend a promote when another session is already doing it!!!" The one exception is a genuinely urgent reason to promote now -- a fix that something live is broken without, say -- and then item 1 names that reason concretely; "it hasn't been fully tested yet" is not one, because that is what every change on pre-staging is. Morgan, 2026-09-25 (strength: decided): *"promotion should NEVER be a blocker to archive a session (unless there is a very urgent reason to do so). Promotion is about the pipeline to get it to live, and that shouldn't stop us from closing a session."*
3. **No Routine is bound to this session.** A Routine created with `persistent_session_id` fires into one named session, and an archived session accepts no events -- check `list_triggers` before adding these seven items or saying the archive line. A Routine that spawns a fresh session on each firing is unaffected.

When all three hold, add, still in order, after the three above:

6. **Branches safe to delete**, scoped to this thread's own work only -- a branch the session itself merged, or one safe on other grounds (its pull request merged or was superseded, discovered rather than performed by this session). **Every branch named here is a one-click delete link, never a bare name**: the filtered branches-page form [branch-delete-links](branch-delete-links.md) specifies, in full and not restated here, with the merged pull request's own page given alongside it where there is one -- never instead of it. Omit the item entirely when there is nothing to flag -- never write that there was nothing.

   **This item is a recommendation and never a blocker, and the distinction is the point of putting it down here rather than in item 1.** An undeleted branch never appears in "Your next steps", never appears in "What's blocking", and is **never** a reason to say "Don't archive this session" -- a reply may say a branch is safe to delete and, in the same breath, that the session can be archived. Morgan, 2026-09-21 (strength: decided): *"it should not consider deleting the branches a 'blocker' - it's something good to do and recommended, but not blocking."* And the session never offers to do the deletion itself, because it cannot -- [never-delete-a-remote-branch](never-delete-a-remote-branch.md).
7. **Other sessions on the same issue**, if any are known to be live on it: "Other relevant sessions to keep an eye on:" with a link to each. Only sessions on *this* thread's own subject -- never a passing mention of unrelated work happening elsewhere. Omit when there are none.
8. **Sessions this one spawned**, if any, each with its link. Omit entirely when this session spawned nothing -- most sessions do not, and saying so every time is exactly the noise this rule exists to avoid.
9. **A practice idea, at most one**, and only when all four hold: something was actually merged this session; the rule came from this session's own work, not a general good idea or something noticed elsewhere; and it has not already been raised in this closing list under a different bullet. State it in one sentence, gently, as a suggestion rather than a decision already made. Most closes have nothing here, and that is the ordinary case, not a gap.
10. **A Todo worth a look, at most one**, and only if it is a good fit: something in the open-items file that bears on this thread's own subject, or, failing that, an item explicitly marked urgent or important. Introduce it as a change of subject -- "Here's an unrelated Todo you might want to look at:" or "Here's a less important Todo you might want to look at:" -- with its link. Say nothing when neither kind of item exists.
11. **A compact check.** Say "Now is a good time to compact the session." when compacting would genuinely help and this is a clean point to do it: the conversation has grown long, the thread has landed something, and what comes next does not depend on how this one was reached. **When the turn-start reply gate says a compact offer is owed, this bullet is due**: say the sentence if this is a clean point, and if the work is mid-flight, say nothing and give it at the next clean point, since the offer stays owed until it is said. Never say "Not a cheap point to compact" -- the person needs to hear when to compact, not when not to. **Skip this bullet entirely when item 12 is going to say "You can archive this session."** Compacting trims context a session goes on to use; a session about to be archived is not going to use any, so a compact recommendation sitting next to an archive one is not two honest answers, it is a contradiction the person has to resolve themselves.
12. **The archive line, always last, always one of two fixed sentences.** "You can archive this session." when the three conditions above all hold and every other item on this list that could still need the window open has been said and dealt with. Otherwise: "Don't archive this session." **This sentence is never the whole explanation.** By the time it appears, item 1 or item 2 above has already said, concretely, which one it is: an explicit action item blocked on the person (item 1), or something the session itself is still waiting on or has running in the background (item 2). The archive line only names the verdict; the numbered items above it are where the reason actually lives, and a "Don't archive this session" with no reason findable in either one is the exact failure this whole section exists to prevent.

   **The line is the fixed sentence and nothing else -- decide it, never argue it.** No clause after it ("...until you've pasted the prompt"), no sentence before it explaining how the session reached the verdict, and never a word about what a hook, scanner or notice listed or would accept. Whatever the person must do before archiving is already item 1, written as the action itself; whatever the session is still waiting on is already item 2. A person who wants the reasoning asks for it. Morgan, 2026-09-26 (strength: decided): *"You should just decide whether to say to archive this session or not. You do not need to share your thinking about whether, why you came to that conclusion. If I have a question, I will ask. And in that boil down section, it should already say anything that I need to do that would block your archive suggestion."*

**And "the work" in condition 1 means everything in the container, not this session's own deliverable.** A session reads that condition against the clone it has been working in, because that is the clone `git status` answers for and because "the work" reads as "the thing I was asked to do". Both readings are natural and both are too narrow: a container here routinely holds five or six checkouts -- this repo, a second copy of it under a different HOME, one per practice source -- and archiving releases all of them at once. On 2026-09-22 a reply correctly reported its own eight commits pushed, said the archive line, and left six unpushed commits in a source clone it had never looked at. **Run the scanner, in every reply that is about to say the line**; "I pushed my work" is not an answer to the question condition 1 actually asks.

**Only a real blocker can hold the line, and the list of them is closed.** "Don't archive this session" is said for one of these and nothing else: (1) something in the container that somebody wants to keep and that exists only there -- the scanner in condition 1 names it; (2) a Routine bound to this session (condition 3); (3) an action the person owes that the work cannot be finished or made safe without -- a push, a merge, an approval, an answer the session is stopped on; (4) something the session itself still has running or is waiting on. **Everything else is not a blocker and never holds the line**: a branch to delete, first of all -- a used-up branch is housekeeping, a recommendation in item 6, never item 1 and never the reason under this line -- and equally a pending Promote (condition 2), a suggestion, an optional follow-up, a question that does not change the outcome. Morgan, 2026-09-26 (strength: decided): *"if a branch needs a deletion, that should never be a blocker and it should never be a reason to tell the user don't archive this session. Only blockers (such as uncommitted branch) can be used to say that."*

**If the person still owes a blocking action, the archive line is never "You can archive this session" -- no exceptions.** A push, a merge, an approval, an answer the session cannot proceed without -- anything named in item 1 as still theirs to do before this is actually safe or done fails condition 1 or 2 above on its own, and the line is "Don't archive this session" every time, full stop, until that action is taken and confirmed. This is not a new condition -- it is the existing three read correctly -- but it is stated here on its own, in words that cannot be softened into "probably fine to close," because the fixed sentence is exactly the part a session under-reads when the rest of the reply feels finished.

**Items 11 and 12, and the compact offer below, are recommendations, not a binding shape.** Give the honest answer after actually reviewing which situation applies -- if the session can be archived, say so; if it can't, say so; if this is a good point to compact, say so -- but nothing here refuses a turn for omitting one. `reply_check.json` still NAMES an unmet one (`--explain` shows it, `advisory: true`), and tools/precedent_reply_check.py still detects it, but neither blocks on it -- unlike the heading in the rule above, which still does. This changed 2026-09-17, on Morgan's own instruction after this gate blocked several turns over content it had no way to know was true or false; see Story.

**Never comment ON the gate itself.** No "I'm not going to say the archive line," no explaining that a requirement is advisory, no narrating compliance or refusal of it -- give the assessment, or leave the bullet out because it plainly does not apply, the same way every other optional item on this list is handled. The gate is plumbing; talking about the plumbing in a reply is exactly the kind of thing this whole practice exists to keep out of the person's way.

**When a compact offer is owed.** Once this conversation has grown 100,000 tokens since a reply last said "Now is a good time to compact the session." (or "This is a cheap point to compact", the older wording, which still counts), the offer is owed. **The session does not have to guess whether it is**: the turn-start reply gate reads the transcript and prints "a compact offer is owed" in that turn, and prints nothing about compacting otherwise. Item 11 is then due, as it says, and stays due turn after turn until it is given. **The one exception is unchanged: a reply whose own archive line says "You can archive this session" says nothing about compacting at all.**

## Detail
**Why one section instead of several practices.** The six things this replaces were six separately-triggered rules, most of them reachable only through the reply gate, several of them enforced only in prose. Reading them side by side, they describe one artifact -- the closing block of a reply -- not six independent occasions. Naming it once, with a fixed name and a fixed order, is what makes it checkable: a bullet either appears in the right slot or it does not, which "a reply that made a commit should restate outstanding items" never quite was.

**"The Boildown" is deliberately not "Next Steps."** Everything in a reply is arguably "for" the person reading it, so a section literally titled that way names nothing -- and the phrase itself has an unrelated, friendlier reading that has nothing to do with a status report. "The Boildown" names what the section actually is: the reply reduced to what still needs a decision or an action, nothing else strained out. The first bullet under it is titled "Your next steps" for the same reason the whole section is not: within a section that already carries several kinds of information, the one bullet that is unambiguously the reader's own action items needs to say so on its own.

**Where the six inherited items came from, briefly, since their own files carry the full reasoning:**
- The plain-words self-contained ask, the recommendation riding alongside every decision, the repository-and-branch naming, and the "say explicitly when there's nothing" line all came from `next-steps-after-commit` and `asks-stand-alone`.
- The practice-suggestion bullet's four conditions are `merged-session-offers-a-practice`'s, unchanged.
- The spawned/other-session links and the three-things-always shape for a handoff (repository, exact paste text, way back) are `handoff-is-pasteable`'s.
- The one-unrelated-item cap on the Todo bullet, and its restriction to the closing reply only, are `closing-items-are-this-thread`'s.
- The three archive conditions, the ambiguous-case resolution (a minor suggestion or a question that doesn't change the outcome does not block an archive), and the fact that archiving buys back no compute, are `archive-a-finished-session`'s.

**What did not move here.** `session-spend-follows-the-task`'s guidance on picking a model for a spawned session's job is a different occasion -- it happens at session *creation*, not at the close of a reply -- and stays where it is, narrowed to just that half. Only its compact-offer clause and the mechanical requirement built for it moved into this practice.

## Why
Six practices asking for six related things, loaded through five different channels (a bare `gates: ["reply"]` registration, an occasion-index entry, a private individual set, a second private individual set, and a JSON declaration each of `reply_check.json` and `close_detect.json`), produced exactly what you would expect: some of it landed every time, some of it only when a session happened to recognize the occasion, and telling which was which meant reading five files. One section, one heading, one fixed order removes that question -- either the bullet the person is looking for is in its slot, or the practice was not followed, and there is no third case to puzzle over.

## Story
Raised by Morgan, 2026-09-15, opening the conversation that produced this file by naming the thing he already loved -- a closing "Next Steps" section -- and the thing wrong with it: *"it isn't consistent enough, (and I think it lives among various different Practices), so I'd like to clean it up and organize it."* He specified both shapes in full before any file was touched: the always-present three items, and the six more that a closing reply adds before its archive line, each with its own wording and its own reason for being there or not.

Two design questions came out of the discussion rather than his initial message. ## Install
Enforced the same way `next-steps-after-commit` and `session-spend-follows-the-task` were, with one change since 2026-09-17: `reply_check.json` declares the required heading pattern (still blocking) and the two fixed sentence-pairs (archive, compact -- now `advisory: true`, each its own entry), and [tools/precedent_reply_check.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_reply_check.py) refuses a reply missing the heading via the Stop hook, same as before, but only NAMES an unmet advisory sentence rather than refusing over it -- `violations()` still detects it, `main()` no longer lets it into the blocking set. `close_detect.json` declares this practice's slug and the archive-ready phrase for [tools/precedent_close_detect.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_close_detect.py), which still gates the practice-idea bullet on real evidence from the session's own transcript rather than on the occasion alone. Neither script needed changing for the original consolidation -- only the JSON declarations moved, from the two practices this absorbs to this one; [tools/precedent_reply_check.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_reply_check.py) itself changed only for the 2026-09-17 advisory split.

**The compact offer is worked out before the reply, not checked after it** (2026-09-28). `reply-gate.sh`, at UserPromptSubmit, passes the hook's `transcript_path` to [tools/precedent_gate.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_gate.py) as `PRECEDENT_TRANSCRIPT_PATH`, and the reply gate runs the same `offer_is_due()` the stop hook uses. Owed: it prints that the offer is owed and how far the conversation has grown. Not owed: it prints nothing about compacting. No transcript (an older hook, a hand run): it says it could not tell, rather than claiming the stop hook will.

What stays a matter of judgment, as it always was: whether an ask is genuinely self-contained, whether a recommendation is real rather than filler, whether a Todo is a good enough fit to mention, whether a moment is actually cheap to compact, and, since 2026-09-20, whether a "Don't archive this session" line has a real reason sitting in item 1 or item 2 above it. That last one was tried against the existing mechanism before being left this way: `require_one_of` can detect the fixed sentence, but detecting whether the *surrounding prose* names a concrete action versus reads as a content-free recap is the same unsolved problem as "is this recommendation real rather than filler" two items over -- no regex distinguishes "waiting on the billing number you're pulling" from three bullets that happen to precede the sentence. No script can read a chat reply for those; the fixed shape only guarantees the section exists and is in order, which is what makes everything missing from it visible.

**One thing moved OFF that list on 2026-09-22, and only one**: whether archive condition 1 holds. The archive VERDICT is still a judgment call for exactly the reasons above -- it turns on whether a loose end is blocking, which no regex reads. But condition 1 is not a reading of the reply at all; it is a question about the disk, and [tools/precedent_container_safe.py](https://github.com/alex137/BestPractice/blob/staging/tools/precedent_container_safe.py) answers it by looking: every git checkout the container holds, scanned for uncommitted changes, untracked files, and commits no remote can reach. `reply_check.json`'s `require_container_safe_if_says` runs it whenever a reply says "You can archive this session" and refuses the turn -- blocking, unlike the sentence requirement it sits beside -- naming each checkout and what is only there. Engine output a refresh writes into a source clone and deliberately never commits is excluded, via `precedent_refresh_sources.classify_dirt`, which is the one definition of which paths those are; counting it would make every clone permanently unsafe and teach a session to ignore the answer. An engine vendored before the scanner existed reports nothing and blocks nothing, the same way an unknown predicate does.
