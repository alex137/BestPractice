## Rule
Every project a session works in gets both halves of a freshness guard wired into its own harness settings: a session-start hook that fetches and, where the update is provably lossless, fast-forwards the checkout before anything is read; and a before-tool hook that re-checks once, on the session's first tool call, and refuses that call when the checkout cannot be vouched for. "Stale" means two independent things and both are checked: behind `origin/<this branch>`, and — the one that actually catches it — missing commits from `origin/<the base branch>`, which a branch that is perfectly in sync with its own remote can still be.

The base branch is passed to the guard explicitly, as an argument, in the settings file. Never detected from `origin/HEAD`, and never assumed to be `main`.

A repository the session merely has **attached** — added mid-session, or cloned by a hook — is checked too, named in `PRECEDENT_FRESHNESS_ALSO` as `<path>=<base branch>` entries separated by `;`. A hook only ever fires for the project dir, so a repo whose own settings are never read is otherwise invisible to its own guard; an environment variable is what follows a session into every repository it touches. A leading `~` in an entry's path is expanded from `$HOME` by the guard itself, because nothing else will: the variable is typed into a settings field and handed to the hook with no shell in between, so an unexpanded tilde reads as a configured entry and checks nothing. An entry naming somewhere that is not a git repository is noted and skipped, never blocked on.

The automatic half is `git merge --ff-only`, when the fetch succeeded, the working tree is clean, and the branch holds nothing `origin` doesn't. **A diverged branch on a clean tree may also be merged automatically** — a plain `git merge origin/<branch>` that keeps both sides' commits on the branch, with the pre-merge tip saved to its own ref first and the merge aborted if it conflicts. Nothing else is automatic: a dirty tree, a stale base and a conflicting merge are reported and left to the person or to a deliberate command. **Never `reset --hard`, `git pull` or `rebase`** — each settles a divergence by picking a side or rewriting history.

## Detail
The two hooks fail in opposite directions, deliberately. The session-start half always exits 0: a hook that can wedge a session over a freshness question is a worse failure than the staleness it guards against, the same fail-gracefully contract every session-start hook is held to. The pre-write half refuses — in Claude Code, a `PreToolUse` hook exiting 2, which hands its stderr back as the reason — including when it could not reach `origin` at all. A check that could not run is not a check that passed, and this is the one place where saying so out loud is cheap: the block is recoverable, one tool call later.

"Could not run" has to mean the state where the guard genuinely cannot tell, and a branch created locally and not yet pushed is not that state: it has no counterpart on `origin`, so there is nothing for it to be behind, and the branch comparison has no question to answer. `git fetch origin <branch>` cannot tell the two apart — it fails identically for an unreachable remote and for a remote that answered "no such branch" — so the guard asks `git ls-remote --exit-code` instead, whose exit status separates them: `2` for an absent branch, anything else for a remote it could not talk to. Skipping the branch comparison there never skips the **base** check, which is the half carrying all the weight on a new branch anyway.

It is recoverable because a `git` command is never blocked. Every remedy the guard names, and the `git config precedent.freshness.override true` escape hatch, is a git invocation; gating those would leave a session unable to run the only commands that could clear the block. The single exception to failing closed is a hook payload the guard cannot read — with no `jq` and no `python3` it cannot recognise a git command either, so blocking there would be that same deadlock, and it exits 0 with a note saying the check was skipped rather than passed. That note names which of the two happened, and the distinction is the whole value of it: an EMPTY payload means the guard ran outside the harness with nothing on stdin, and saying "no jq, no python3" there sends whoever reads it hunting for two tools that are installed.

The before-tool matcher includes the shell tool (`Bash`, in Claude Code). An agent in a mode where file edits go through `cat`, `sed` or `python3` in a shell never touches the edit tools at all, and a matcher naming only those is perfectly blind to every change it makes. This is not write-detection — trying to decide from a command string whether it writes is a losing game — it is a gate that fires once and then costs one file-existence test for the rest of the session.

Two mechanical traps the guard is written around, both learned the expensive way and recorded in this repository's [gotchas/](https://github.com/alex137/BestPractice/blob/staging/gotchas/INDEX.md). `git rev-parse <missing-ref>` prints the ref *name* on stdout while exiting non-zero, so every possibly-absent ref goes through `--verify --quiet` instead. And `--depth` is passed only to a clone that is already shallow: handing it to a full clone does not limit a fetch, it truncates the repository into a shallow one — a guard meant to make history reliable, destroying the history every check it runs reads from.

Revised 2026-09-11, on the gap the day's own work walked into. A session rooted in one repository, with another attached, cut a branch in the attached one from a `main` that had moved — and the attached repo's guard was installed, correct, and silent, one directory away, because `CLAUDE_PROJECT_DIR` pointed at the other repo so the attached repo's settings were never read. Nothing was lost that time; the same shape is what the Why records costing a session a day.

The fix is deliberately the same shape as the one the commit-identity chain already uses for the same problem: [tools/precedent_identity.py](../tools/precedent_identity.py) checks `PRECEDENT_COMMIT_*` before anything that needs a clone or a hook, precisely because environment variables cross repository boundaries and hooks do not. `PRECEDENT_FRESHNESS_ALSO` is that rung for freshness. It is opt-in, and the entries carry their own base branch for the same reason the hook takes one as an argument — the base is not detectable, and a repository pinned to a branch other than its default is where detection gets it wrong.

What it does **not** fix, and this is the honest limit: the variable has to be set on the environment, so the first session in an environment that lacks it is unguarded exactly as before. There is no mechanism by which a repository can require its own guard to run in a session rooted somewhere else.

## Why
The failure this exists for is not a branch that has fallen behind its own remote. It is a container that came up on a clone days old, where nothing looks behind because the branch and its remote counterpart are equally out of date, and the work then proceeds against code that has since moved — in the worst recorded case, a session concluding that files merged the week before "did not exist". A session-start warning was already there for that, and it was not enough twice: it prints before any of the work, sixty lines into startup output, and acting on it is left to whoever reads it. A gate on the first write is the same information at the moment it is impossible to skip.

The fast-forward is the smallest part on purpose. Under its four preconditions it cannot lose anything and cannot conflict, so it is free — but it fires only in the case where the warning was already easy to act on. The base-branch comparison is the one that closes the actual hole, and it stays a report rather than an action, because merging a base into a branch is a real merge and a guard should not be resolving those unasked.

## Story
Raised 2026-09-06, after Morgan asked whether BestPractice checked for a stale branch at session start and what it would take to have his individual practice set not just check but update itself before touching anything. BestPractice did check: its [session-start hook](https://github.com/alex137/BestPractice/blob/staging/.claude/hooks/session-start.sh) fetches the current branch and warns, a guard added after a session there found its local branch sharing zero commits with origin, and hardened again after a container came up five days and 207 commits stale with the hook silent because its own fetch had failed. What that guard still could not see was a branch cut from a stale base: it compared `HEAD` against `origin/<the same branch name>` and nothing else, so on a feature branch — which is every working session there — it either compared against a ref that did not exist yet and silently checked nothing, or compared against one that was equally old and reported everything fine. The individual set had no check of any kind, so a session working *in* it ran with nothing watching, while the copy of it other projects resolve had been quietly fast-forwarding itself at every session start for weeks.

Revised 2026-09-10, on the first thing this guard actually cost. A session opened on a newly created branch had its very first tool call refused: the branch had never been pushed, so `git fetch origin <branch>` could not succeed, so the pre-write half concluded it could not verify anything and blocked — correctly, by the letter of the Detail as it then stood, which said "including when it simply could not fetch". The two remedies it named were both wrong for the case: pushing the branch just to satisfy a hook is premature, and the other was the override, which is the one habit this practice cannot survive teaching. A gate that can only be ignored trains everyone to skip the one check that would have caught something real.

Worth recording that the fix immediately earned itself back. With the branch comparison correctly skipped, the base check ran for the first time in that session and caught `main` two commits ahead — exactly the stale-base case this practice was written for, on the very branch whose block had been spurious.

**Amended 2026-09-23: a diverged branch may be merged.** The rule used to allow only a fast-forward, so a diverged branch was always reported and left. BestPractice's own guard had meanwhile gone further twice: on 2026-09-15 it reset a diverged clean branch to `origin` at session start, and on 2026-09-22 it began merging one mid-session, after reporting-only left the drift in place, every prompt re-reported it, and a stale clone had to be reconciled by hand. The reset broke this rule by name and was removed on 2026-09-23. The merge did not break it in spirit, since it keeps both sides and picks neither. The wording was changed to say so, on a session's recommendation, which Morgan accepted.

**Where it has lived.** Landed first in Morgan's individual set, moved on 2026-09-23 to the shared set for repository maintenance, and **moved here on 2026-09-28**, on Morgan's accepting a session's recommendation that it applies to any repository, not only to maintaining practice sets. The engine had been shipping the mechanism since 2026-09-06, with a header saying the rule it implements was not yet a universal practice; it is now. The rule text was rewritten from Morgan's first person, and its Install now points at the engine's own guard rather than the set's copy.

## Install
The mechanism is the engine's own guard, [templates/harness/claude-code/hooks/freshness-guard.sh](https://github.com/alex137/BestPractice/blob/staging/templates/harness/claude-code/hooks/freshness-guard.sh), wired three times in the Claude Code adapter's [settings.json](https://github.com/alex137/BestPractice/blob/staging/templates/harness/claude-code/settings.json): session-start, a throttled re-check on each submitted prompt (for a session left open across a break), and pre-write. [tools/precedent_vendor_engine.py](../tools/precedent_vendor_engine.py)'s hook wiring installs it into a consuming repo and adds a missing entry on each refresh; replace the base branch argument on all three entries with the repo's real base branch. A repo that declines it says so, with the reason, in `precedent.json`'s `declined_adapters`.

No `checked_by` at this level. The engine's own harness keeps its two copies of the guard identical and exercises it against fixtures, which covers the mechanism, not a consuming repo's wiring. The shared set this rule moved from carries a tree-scope check that runs the guard in throwaway repositories — an unreachable remote, a reachable remote with no such branch, a stale attached repo — and asserts its structural invariants; that check tests the set's own copy of the guard, and did not move with the rule.
