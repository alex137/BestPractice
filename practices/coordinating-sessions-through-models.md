## Rule
**When several sessions work on one repository, what they share is written once, in a file a tool reads, and never carried in messages or kept in the coordinator's head.**

1. **A choice every worker depends on lives in one registry file every script reads** ([registry-source-of-truth](registry-source-of-truth.md)). A decision is a one-line change there. No message to a worker carries the value, and no script types it in.
2. **A quantity two notes need has one home.** The second note reads it from the first, or asserts that its own equals the first's ([scripts-assert-properties](scripts-assert-properties.md)).
3. **One quantity has one name.** A new entry is compared with every entry already there before it is added, and a check lists any two differently named entries that carry the same value and unit. Each pair listed is merged, or recorded as different with the reason.
4. **One committed command rebuilds everything, in an order it works out itself** from what each step reads and writes. The order is never kept by hand, and never in a scratch folder ([repo-is-memory](repo-is-memory.md)).
5. **A session takes another session's files as they are.** It never regenerates them on its own branch.
6. **A check for anything dropped runs before every push:** a figure, marker or block another script reads that this change removed.
7. **The coordinator reports only figures a script printed, and only settled ones.** Anything else is called "not yet computed". A headline names the unverified assumptions it rests on ([numbers-are-sourced](numbers-are-sourced.md)).

## Detail
**Three kinds of session, and who opens which.** A project worked by more than a few sessions has:

- **The conversation session.** The one the person opened and talks in. It talks to the person and to the coordinator and to nobody else. It passes the person's requests on as tasks, and it opens each coordinator.
- **The coordinator.** One at a time. It tasks the workers, takes their reports, lands their work, and writes to the conversation session only on a landing, a changed conclusion or a decision that is the person's. It opens every worker.
- **The workers.** Each does one unit of work on its own branch and reports to the coordinator, never to the conversation session and never to the person.

**The coordinator is a role that sessions take in turn.** A coordinator is replaced when it reaches the size the project declares, not when something goes wrong: the next one is opened by the conversation session, fresh, and starts from the handoff file on the landing branch. The file names the session that holds the role now. So a worker finds its coordinator in that file, never from which session created it, and a worker opened by an earlier shift reports to the present one.

**Who the coordinator is, for a session asking.** In a project that keeps a handoff file, the session it names. Where there is none, the session that created this one, for as long as that session is running. A session the person opened themselves has no coordinator above it: it is the conversation session, and the coordinator too until it hands that role to a session of its own ("The person's thread is never the switchboard").

**New sessions are opened from above, never sideways.** A worker that needs a further session, to carry on its own work or for work it noticed, asks the coordinator to open it. A coordinator that is handing over asks the conversation session to open its successor. Neither opens its own: a session opened that way hangs under one that is about to finish, outlives it, and is on nobody's list of sessions to archive ([prompt-please](prompt-please.md), "A sibling, not a child").

**The registry is for choices, not results.** Which design leads, what it is measured against, which variant is the baseline: these are decisions the person makes and changes. Each script reads them and computes from them. A check flags any note that quotes a figure computed for a different choice than the registry now holds, so a changed decision shows up as a list of notes to rebuild, not as a round of messages.

**An assumption's evidence belongs to the design it was run on.** Each assumption a headline rests on is listed in the registry beside the design its evidence came from. When the design changes, that evidence is marked as an earlier design's until it is run again. Evidence gathered on one design and quoted for another looks exactly like evidence.

**Twins are caught when they are born, or not at all.** Two workers who each need the same quantity will each name it, differently, and both names then live on: every rule about one home is satisfied twice. On the day the second is added the two are still equal, and a comparison of value and unit finds them. Once one has been updated and the other has not, they differ, and no comparison of values will ever pair them again. So the check runs when an entry is added and before every push, each entry says in a line what it measures so a reader can match by meaning, and a pair found equal by coincidence is recorded as different so it is not raised twice. Where the build is cheap enough, a stronger test: change each choice in turn and rebuild; two entries that move together under every change are one quantity.

**The full check comes due when the registry changes, never on a clock.** The cheap comparison runs at every push. The full check, which is the reading by meaning and the change-each-choice test, is too slow for that, so the registry records when it last passed, and a change to any entry runs it again once that record is old enough: by age, or by how many entries have changed since, whichever comes first. Both limits are choices written in the registry. A project nobody is changing pays nothing, and one changing fast is checked often. The record is one line for the whole registry, written only by the check itself; a stamp on every entry would be rewritten by every session and collide at every merge.

**The build command learns its order.** It records what each step read and wrote on a real run and orders the steps from that. A step added later needs no entry in anybody's list. Two notes that each read the other are a build failure, named as one: a cycle never settles, and a build that reruns it until the figures stop moving has only hidden that.

**Dependent work waits for settled inputs.** A producer marks an output moving before it changes it, and settled, with the trunk commit and a hash of its content, only after it lands. A consumer reads inputs from trunk's stored results and records the hash it read. Its build refuses to land work built on an input that is not settled or whose hash has changed, and a long run refuses to start on one; a short count may run, stamped as not settled. The coordinator releases work in dependency order from one command that lists what is on hold and why. Nobody keeps that order by hand.

**A headline moves rarely, and only on counted figures.** Before a headline figure moves, every item the registry lists as never counted or never run gets a rough size, largest first, and the headline says how many such items it still leaves out. A figure that would move the headline is counted twice, independently, before it does. Only those figures: counting everything twice is the exhaustive grid again.

**Talk is spend.** Land when a step has settled, never per commit: each landing costs a rebuild, a check and a round of wake-ups. Tell only the sessions whose inputs changed that trunk has moved. A worker reports once per finished unit. Two workers fixing one file talk to each other and tell the coordinator once, at the end. The coordinator writes to the person when something lands, a conclusion changes or a decision is needed, and otherwise says nothing. Every task handed to a session carries a ceiling in time, and the session stops and reports at it: a session cannot see what it has spent, so the ceiling is the brake. Where the harness reports what a worker's turn cost when it ends, the coordinator records it against the landing it served; that record is the only measure of what coordination costs.

**What a session costs is its context times its calls, plus every cold wake.** A session re-reads everything it holds on every call, so the same message costs many times more to send to a session that has worked for days than to a new one, and a session woken after its cache has lapsed pays to write its whole context again before it does anything. Measured in one project: a worker holding about 740,000 tokens paid about a dollar for a six-call turn, and about twelve dollars to be woken after an hour idle. So: a long-lived worker is replaced by a fresh session at the end of a unit, after committing a short handoff beside its work, and a new task goes to a fresh session whenever it can be done from the repository. Nothing is broadcast to idle sessions; what one worker must act on goes to it in one message. The coordinator records each session's cost against each landing and reports a daily total. And when coordination changes hands, the old coordinator says so to each worker first: a worker rightly refuses a session it has never heard from, and each refusal is a paid turn on both sides.

**A long-lived session keeps one short state file current, and hands over from it.** The file sits in the repository beside the session's work and says what it owns, how to build and check it, what is in flight with its prediction, the traps it has met, and what waits on whom. It is brought up to date and pushed at the end of every unit of work, never written on request at the end, so a successor can start at any moment without asking the old session anything. Three things follow. A tasker may retire any session at any time on the strength of that file. A session watches its own size, and at the size its project has declared it finishes its unit, brings the file current, and asks its tasker for a successor, or starts one itself where it has a tool for that; no session can restart itself in place. And a restart from the file is preferred to compacting the old session: compaction keeps the cost of a long history and drops parts of it that nobody chose, where a successor starts small and reads only what was judged worth writing down. The size is the project's own setting, declared where its sessions read it, and no figure is given here ([constants-are-risk-inputs](constants-are-risk-inputs.md)). **If a successor cannot work from the file, the file was wrong**, and that is the test of [repo-is-memory](repo-is-memory.md).

**The session that creates a session archives it.** Once a session it started has its work on the landing branch and its report has been read, the creator archives it, after confirming for itself that nothing exists only there: archiving releases the container, and whatever was only in it is gone. A session that is still running, still waited on, or holding unlanded work is left alone and named in the creator's state file as open. A coordinator that hands over lists the sessions it started and has not archived, so its successor inherits the job with the rest. A session a person started is never archived by another session without that person's word.

**The person's thread is never the switchboard.** A session shows a reply for every message that reaches it, so one that both talks with the person and receives every worker's reports fills the person's thread with relaying, and no rule about staying quiet can hold inside that one thread. Once a session finds itself relaying for more than two or three workers, the coordinating moves to a session of its own. The person's thread stays the conversation. The new coordinator starts from a committed handoff file: who reports to whom, each worker and its branch, how work lands, who owns which file, the standing rules, the limits that are not its to lift, and what is open. Workers are told once to report to the coordinator. The coordinator writes to the conversation only on a landing, a changed conclusion or a decision that is the person's, each message complete in itself, and the person's requests go the other way as tasks. The split is cheap only if the landing scripts and the state already live in the repository.

**Why a session never regenerates another's files.** A branch that rebuilds a file its session does not own carries that file as of its own starting point. Merged, it resets the owner's later work without a conflict, because to git it is simply the newer change.

**Settled, not first.** A worker's first figure is often revised within the hour. A coordinator that passes each first figure on has the person reading a number that is already gone. Report what the build printed after the pieces were put together.

This sits beside [working-in-parallel](working-in-parallel.md), which is about people claiming work in a shared repository, and [tasked-session-stays-reachable](tasked-session-stays-reachable.md), which is about whether a change of plan arrives. This rule makes most changes of plan a registry edit instead of a message.

## Why
Each worker's own work can be a sound model while everything between the workers is done by hand. Then the project's weakest parts are exactly the ones nobody modelled: which choice is current, what order things rebuild in, whose file is whose, and which figure the person was told. Those fail quietly, and they fail every time a decision changes.

## Story
2026-11-23, in a project run by one coordinating session and more than fifteen workers. Every worker kept a note and a script that printed and checked its own figures. The design's choices were changed several times in one day, each time by a message to every worker, and each worker re-pointed its own script by hand. The rebuild order lived in a script in the coordinator's scratch folder. Several landings in a row failed: on rebuild order, on a dropped marker, on a branch that reset other workers' files. The coordinator's reports carried arithmetic done in the chat when a worker's figure was not ready. The person asked whether the work was being done by inference where it should have been a model. The project then built the registry, the build command and the dropped-marker check; the check caught a removed figure another script read before it reached the trunk. Later the same day an assumption turned out to rest on evidence run on a different design than the one being built, which is where the rule about evidence comes from. The next night, about fourteen workers and a coordinator ran all night and usage went past a weekly limit: the headline had moved five times, dependent work had started on inputs that were still moving, and one small fix to a shared file cost the coordinator about ten turns of relaying. The paragraphs on settled inputs, on moving a headline and on talk come from that night. The day after, the person came back to a thread they could not read: the coordinator's replies to every worker report sat between them and their own conversation. The coordinating was moved to a session of its own. Reading one worker's recorded costs afterwards gave the figures in the paragraph on what a session costs; that session alone had cost about $644 at list price, and eight workers had refused the new coordinator because nobody had told them it was coming.

**2026-11-25: the state file.** A project spent a day replacing long sessions with fresh ones by hand. Fresh sessions did a unit of work for a few dollars where an old one cost several times that for a single turn after sitting idle, and three coordinators in a row were replaced cleanly at about the same size, each from a handoff file. The files were the weak point: written on request, sometimes by a third session from notes, because waking the old session cost more than writing its file for it. Automatic compaction on those sessions was set to begin far later than the point where a restart was already cheaper. Alex asked whether each session should save what it is doing so it can be restarted, and whether that beats compression; proposed here as a state file kept current at every unit, he said yes. The figures are that project's own.

**2026-11-27: who archives.** The person a project belongs to asked a session whether two measurement threads were its own, and whether it was done with them. They were not its own, and nothing recorded whose they were or whether they were finished. His list of recent sessions held dozens that coordinators had started, and no rule said who closes one. He asked whether a session should archive the sessions it creates once they are no longer needed; proposed as the paragraph above, he agreed.

**2026-11-27: who the coordinator is.** The Rule and this Detail had used the word since the practice landed without saying which session it meant. A worker that was finishing opened its own successor, which made the new session its child. Alex, the same day, proposed that opening a session route through "whatever is the current coordinator thread", and, asked whether to land that: "If we already have the concept of a coordinator as a best-practice then yes go ahead on the sibing rule. If not then we need both." The word was in use and undefined, so both were written: the definition here, and the rule in [prompt-please](prompt-please.md).

**2026-11-27: the pattern already in use.** Asked the same day whether the coordinator should have a tag of its own, Alex: "yes on coordinatote. it seems like we should match the pattern we developed for the way the coordinator has been working with this [project] operating as an interface to a series of coordinators that keep being replaced." (strength: decided). The project that prompted this practice had by then run nine coordinators in turn, each opened by the one session its owner talks in, each starting from the handoff file on its landing branch and retired for its size alone, with the workers reporting only to whichever held the role. The definition written that morning had said a worker's coordinator is the session that created it, which that project's own file contradicts: a worker opened by one shift reports to the next. The three kinds of session, who opens which, and the tag were written from what the project does.

## Install
Nothing to install from here. The registry file, the build command and the dropped-marker check are the project's own, written for what it builds. A coordinating session loads this rule when it starts tasking workers, and says in each worker's brief where the registry is and that no message will carry a choice.
